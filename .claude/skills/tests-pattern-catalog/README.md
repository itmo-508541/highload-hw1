# tests-pattern-catalog — зачем и как этим пользоваться

Человеческая часть скилла: идея и порядок применения. Сам `SKILL.md` на этот
файл не ссылается — модель его не читает.

## Идея

Каталог `patterns/tests/` фиксирует **механики проверки**, а не поведение
домена: как устроен тест на HTTP-экран, на консольную команду, на контракт
JSON — и как такой тест устроен быть не должен. Каждая карточка указывает
на donor — маленький существующий тест того же вида, который копируют.

Смысл в том, чтобы новый тест писался по эталону, а не по стилю соседнего
файла: сосед может быть большим, устаревшим или ошибочным, а карточка отобрана
человеком под конкретный класс ошибки.

Карточки заводятся не «на всякий случай» и не задним числом из суррогатного
теста. Поводом служит разобранный класс ошибки: тест, который получился удачным,
или тест, который был исправлен после ревью. Поэтому карточку всегда назначает
человек, а `SKILL.md` запрещает писать её без такого указания
(`disable-model-invocation: true` — скилл не подхватывается моделью сам).

## Кто читает каталог

Скиллы `phpunit-tests` и `behat-tests` вторым шагом своего рабочего цикла
открывают `patterns/tests/INDEX.md` и, если нужный вид проверки там есть,
работают по карточке. Обратной связи нет: `tests-pattern-catalog` не знает
о них и не вызывает их, а они не вызывают его. Связь — через формат каталога
(`patterns/tests/CLAUDE.md` и схема карточки), порядок вызова задаёт человек
в чате. Это позволяет наполнять каталог и писать тесты в разных сессиях
и разными людьми.

## Порядок применения

Всё начинается после того, как задачи change реализованы.

**Шаг 1.** В новом чате прогнать проверку change:

```
/openspec-verify-change
```

**Шаг 2.** Когда вердикт положительный — заказать ревью кода и вернуть в работу
то, что сделано неверно или неполно:

```
/code-review проанализируй код этого change

По результатам ревью убери [x] у задач в tasks.md, которые ты посчитаешь
выполненными неверно или неполно
```

**Шаг 3.** Прочитать результат ревью самому и запустить исправления:

```
/openspec-apply-change
```

**Шаг 4.** После финальных исправлений — отобрать кандидатов в каталог. Анализ
делается **до** вызова скилла и без него, чтобы кандидаты появились из решений
change, а не из желания заполнить каталог:

```
У нас в проекте есть каталог @patterns/tests , прочитай его предназначение
в файле @patterns/tests/CLAUDE.md

Проанализируй решения этого change в части тестирования кода. Подскажи, какие
из них можно считать сильными по содержанию и форме кандидатами на добавление
в этот каталог и почему?
```

**Шаг 5.** Выбрать из предложенного и назвать скиллу конкретную карточку:

```
/tests-pattern-catalog добавь карточки <...>
```

Шаг 4 отделён от шага 5 намеренно: на шаге 4 модель предлагает, на шаге 5
человек называет класс ошибки. Без шага 5 скилл писать файлы не должен.
