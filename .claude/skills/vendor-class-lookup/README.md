# vendor-class-lookup — обоснование

Этот файл для человека: зачем скилл существует, почему сформулирован именно так
и на каких замерах основан. Из `SKILL.md` он не упоминается, чтобы ассистент его
не читал — там остаётся только то, что меняет действия модели.

## Какую проблему закрывает

Не «неудобно искать в `vendor/`». Скилл закрывает генерацию кода под чужую
мажорную версию библиотеки: в шаблоне зафиксированы `sonata-project/admin-bundle`
4.43 при Symfony 7.4 и PHP 8.4, а в тренировочных данных моделей много кода
под Sonata 3.x. Восстановленный по памяти API даёт неверные неймспейсы
и сигнатуры, и такой код проходит ревью, а падает в рантайме или на автолоадере.

Пример расхождения, проверенный по установленному пакету: в 4.43
`AbstractAdmin::configureRoutes()` принимает `RouteCollectionInterface`,
а не `RouteCollection` из 3.x, и админка регистрируется атрибутом тега
`model_class` (`config/services.yaml`), а не тремя аргументами конструктора
`[~, App\Entity\User, ~]`. Обе формы 3.x модель воспроизводит уверенно.

## Почему триггер описан через незнание, а не через `vendor/`

Первая редакция скилла активировалась на формулировки
«поиск класса в `vendor/`», «поиск зависимости», «autoload, classmap». Все они
предполагают уже известный ответ: в момент, когда ассистент читает `use ...`
в чужом файле, он ещё не знает, где определение, — расположение это результат
поиска, а не входное условие. Такой триггер не срабатывает там, где нужен.

Отсюда же следует, какой режим отказа считать главным. Не «искал и не нашёл»,
а **«не искал вовсе»**: пустой результат хотя бы заметен, а молчаливое обращение
к памяти вместо источника — нет.

## Почему PSR-4 идёт первым, а классмап вторым

В оригинальном скилле порядок был обратный, с запретом на рекурсивный обход
`vendor/` ради экономии. Но полнота классмапа зависит от флага: без
`optimize-autoloader` в нём лежат только классы из секций `classmap`,
и первым шагом он почти всегда пустой. В шаблоне флаг включён
(`autoload_classmap.php` — 9784 строки, 423 записи Sonata), но новый проект
может его выключить. `autoload_psr4.php` есть всегда — 144 префикса, включая
`Sonata\AdminBundle\ => vendor/sonata-project/admin-bundle/src`, — поэтому
он и идёт первым.

Экономии, ради которой строился строгий протокол «классмап → PSR-4 → lock,
без лишних волн попыток», здесь тоже нет. Замеры на этом `vendor/` (156 МБ,
13464 PHP-файла):

| Операция | Время |
|---|---|
| рекурсивный поиск по всему `vendor/` | 0,04 с |
| поиск по `autoload_classmap.php` | < 0,01 с |

Разница в абсолютных величинах пренебрежима, поэтому от протокольной части
и от HITL-церемонии оригинала осталось только правило «путь берётся из артефактов
Composer, а не угадывается».

## Почему обход — именно явный путь

Проверено на ripgrep 14.1.0 и на поисковой обёртке Claude Code: правила
`.gitignore` применяются при обходе дерева, но не к пути, переданному в аргументах.

```
поиск от корня проекта   → пусто, код возврата 0
тот же шаблон, путь vendor/ → файл найден
```

Поэтому основной приём в скилле — явный путь, а `--no-ignore` и `command grep`
даны как запасные: они зависят от инструмента, явный путь — нет.

## Перенос в другой проект

Файлы переносятся без правок, но проектно-зависимы три утверждения этого
README: состояние `optimize-autoloader`, версии пакетов и пример с Sonata.
При переносе в проект с другим стеком их нужно перепроверить.
