# PHPUnit

Конфигурация, конвенции и карта suite'ов — в `tests/CLAUDE.md`.

## Что на входе

Строка «Стратегии тестирования»: инструмент, suite, тип теста, что нужно снаружи,
базовый класс, обоснование. Приходит из `design.md` или прямо из чата — источник
неважен, важен состав.

Полей не хватает (не названы suite или тип теста, а пользователь не указал файл
явно) — **вызвать скилл `testing-strategy`** и работать по его ответу. Не
достраивать недостающее самому.

Тип `characterization` бывает двух видов, и различие переносится в тест: фиксация
нормального поведения и фиксация **дефектного**. Какие строки фиксируют дефект,
стратегия называет в разделе «Решения».

## Рабочий цикл

1. Прочитать `tests/CLAUDE.md` — карту и конвенции. Делать это явно: вложенный
   `CLAUDE.md` подхватывается только при обращении к файлам своего каталога,
   на запись нового файла автоподхват не срабатывает.
2. Открыть `patterns/tests/INDEX.md` — оглавление механик проверки. Есть строка
   под нужный вид проверки — работать по её карточке: копировать её donor
   и соблюдать её секцию `Do not`. Нет такой строки — писать тест без карточки;
   карточки в каталог в этом прогоне не добавлять.
3. Прочитать `PHPUnit13.md` в каталоге этого скилла — Model Knowledge Patch
   для той версии, что стоит в проекте (PHPUnit 13.2). Перед написанием теста,
   а не после его падения. Патчи соседних мажоров (`PHPUnit10`…`PHPUnit12`)
   нужны только при разборе чужого кода на той версии. Как патч собирается
   и обновляется — `BUILD.md`, `COLLECT.md`, `README.md` в этом же каталоге;
   на прогон теста они не нужны.
4. Найти существующий тест или создать `*Test.php` в каталоге suite
   из входной строки; зеркальность структуры — по `tests/CLAUDE.md`.
5. Написать тест по конвенциям `tests/CLAUDE.md`: базовый класс, namespace
   и место фикстур заданы там.
   Тест, фиксирующий **дефектное** поведение, несёт это в docblock: описание
   дефекта и строку «обязан быть переписан при исправлении». Иначе зелёный тест,
   требующий сломанного поведения, читается как одобрение этого поведения,
   а его будущее падение — как поломка теста.
   Описание пишется самодостаточным. Идентификатор риска из карты (`R<n>`)
   в docblock не переносится: он разрешается только внутри своего change,
   а тест переживёт его — переносится описание, а не номер.
6. Прогнать командой из `tests/CLAUDE.md`.
7. Максимум три попытки. Не вышло — остановиться, показать вывод прогона
   и ждать указаний.

## Что не делать

- Не выбирать инструмент и suite самому — это `testing-strategy`.
- Не определять базовый класс «по стилю соседних тестов»: он следует из suite.
- Не править `phpunit.dist.xml`, `Makefile`, `.gitlab-ci.yml` или конфигурацию
  приложения ради своего теста.
- Не переносить и не переписывать чужие тесты попутно; замеченное несоответствие
  suite — отдельная задача, а не часть текущей работы.
- Не гнаться за зелёным прогоном ослаблением проверки (убрать assert, заменить
  на `assertTrue(true)`, пометить `markTestSkipped`).

## Чеклист

- [ ] Отклонение от suite, названного во входной строке, согласовано
      с пользователем
- [ ] Тип теста соблюдён: regression падает без исправления, characterization
      проходит и до, и после изменения, тест на новое поведение падал до кода
- [ ] Ни один зелёный тест не описывает сломанное поведение как норму:
      у каждого такого теста в docblock есть описание дефекта
- [ ] Прогон нужной цели зелёный, вывод показан пользователю
- [ ] Пользователю названы путь к файлу и результат прогона
