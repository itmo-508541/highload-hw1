# Behat

Конфигурация, конвенции, реестр доменов и таблица тегов — в `features/CLAUDE.md`.

## Что на входе

Строка «Стратегии тестирования»: инструмент, домен, теги, feature-файл, контекст,
тип теста, обоснование. Приходит из `design.md` или прямо из чата.

Полей не хватает (не названы актор, домен или необходимость браузера, а пользователь
не указал файл явно) — **вызвать скилл `testing-strategy`** и работать по его ответу.
Не достраивать недостающее самому.

Тип `characterization` бывает двух видов, и различие переносится в сценарий:
фиксация нормального поведения и фиксация **дефектного**. Какие строки фиксируют
дефект, стратегия называет в разделе «Решения».

## Рабочий цикл

1. Прочитать `features/CLAUDE.md` — реестр доменов, имена файлов, теги, конвенции.
   Делать это явно: вложенный `CLAUDE.md` подхватывается только при обращении
   к файлам своего каталога, на запись нового файла автоподхват не срабатывает.
2. Открыть `patterns/tests/INDEX.md` — оглавление механик проверки. Есть строка
   под нужный вид проверки — работать по её карточке: копировать её donor
   и соблюдать её секцию `Do not`. Нет такой строки — писать тест без карточки;
   карточки в каталог в этом прогоне не добавлять.
3. Написать или изменить `.feature` по правилам имени и keywords
   из `features/CLAUDE.md`. Сценарий формулируется на языке актора,
   а не на языке кода.
4. Проставить теги по таблице `features/CLAUDE.md`.
   Сценарий, фиксирующий **дефектное** поведение, помечается комментарием `#`
   над `Scenario`: описание дефекта и строка «переписать при исправлении».
   Иначе зелёный сценарий, требующий сломанного поведения, читается как описание
   нормы. Описание пишется самодостаточным; идентификатор риска из карты (`R<n>`)
   в сценарий не переносится — он разрешается только внутри своего change,
   а сценарий переживёт его.
5. Реализовать шаги контекстом того домена, что назван во входной строке;
   размещение контекста и оформление шагов — по `features/CLAUDE.md`.
   Существующий подходящий шаг переиспользовать, а не копировать: паттерны
   уникальны глобально, точный дубль роняет Behat на загрузке.
6. Зарегистрировать новый контекст, как велит `features/CLAUDE.md`.
7. Прогнать командой из `features/CLAUDE.md`.
8. Максимум три попытки. Не вышло — остановиться, показать вывод прогона
   и ждать указаний.

## Что не делать

- Не выбирать инструмент, домен и теги самому — это `testing-strategy`.
- Не заводить новый домен молча: домен приходит из реестра, новый — только
  ответом пользователя, и тогда же дописывается строкой в `features/CLAUDE.md`.
- Не писать в Gherkin то, у чего нет актора вне команды разработки: проверки
  сборки, phing-задач и изолированной логики идут в PHPUnit, в `tests/`.
- Не удалять ключ `contexts` из suite в `behat.yml.dist`: без него Behat
  подставит дефолтный `FeatureContext` и упадёт.
- Не править `behat.yml.dist` сверх регистрации своего контекста — кроме
  сессий, если их требует предусловие стратегии тестирования; не трогать
  `Makefile` и `.gitlab-ci.yml`.
- Не подгонять сценарий под реализацию: шаг описывает наблюдаемое поведение,
  а не вызов метода.

## Чеклист

- [ ] Ни один зелёный сценарий не описывает сломанное поведение как норму:
      у каждого такого сценария есть комментарий с описанием дефекта
- [ ] Прогон зелёный, его вывод показан пользователю
- [ ] Пользователю названы пути к `.feature` и контексту и результат прогона
