## Context

Агенты (Cursor, Claude Code, Copilot) при навигации по проекту выполняют
множественные Glob/Grep/Read — каждый вызов стоит токенов и латентности.
Проект уже использует распределённые `AGENTS.md` как routing-слой (каталог →
назначение), но маппинг «requirement → implementation file» отсутствует.

Существующие specs (`openspec/specs/<topic>/spec.md`) описывают поведение,
но не указывают где оно реализовано. See proposal.md — Why.

## Goals / Non-Goals

**Goals:**
- Создать Cursor-скилл `capability-index`, хранящий Capability Map.
- Обеспечить агенту путь от домена до исходного файла за ≤3 операции чтения.
- Формат, удобный для инкрементального обновления и человеческого review.

**Non-Goals:**
- Интеграция в `opsx:archive` как автоматический шаг (будет тестироваться отдельно).
- Symbol-level индексация (call graph, AST parsing).
- Автоматическая валидация актуальности индекса (пока — ответственность Архиватора).

## Decisions

### 1. Гибридный формат: Markdown (INDEX) + YAML (topics)

**Выбор**: INDEX.md — Markdown-таблица; per-topic файлы — YAML.

**Альтернативы**:
- Всё в одном Markdown → не масштабируется при 20+ тематиках, инкрементальный
  update требует перезаписи всего файла.
- Всё в YAML → менее читаемо для человека на верхнем уровне, таблица доменов
  теряет наглядность.
- JSON → многословен, неудобен для diff/review.

**Обоснование**: INDEX.md ≤200 строк — всегда целиком помещается в контекст
агента. YAML-файлы — структурированы, легко парсятся, diff-friendly для PR review.

### 2. Хранение внутри скилла (.cursor/skills/capability-index/)

**Выбор**: Данные индекса лежат в директории скилла.

**Альтернативы**:
- Корень репо (PROJECT_INDEX.md) → загрязняет корень, не привязан к конкретному
  инструменту.
- `openspec/` → смешивает specs (source of truth поведения) с производным
  артефактом (маппинг на реализацию).

**Обоснование**: Скилл — самодостаточная единица; SKILL.md объясняет когда и как
читать, данные рядом. Ссылка из любого AGENTS.md: «см. .cursor/skills/capability-index/».

### 3. Односторонняя навигация без обратных ссылок

**Выбор**: topics/*.yaml НЕ содержат поле `domains`. Связь domain→topic
хранится только в INDEX.md.

**Альтернативы**:
- Дублировать `domains` в каждом topic.yaml → двойное обновление при
  реорганизации доменов, риск рассинхрона.

**Обоснование**: Агент всегда начинает с INDEX.md, обратный путь не нужен.
Source of truth для M:N-связи — единственный файл (INDEX.md).

### 4. Свободный текст для role

**Выбор**: Поле `role` — произвольная строка (1-2 предложения).

**Альтернативы**:
- Фиксированная таксономия (entity, service, controller…) → жёсткая,
  не покрывает все случаи, требует поддержки перечня.

**Обоснование**: Свободный текст проще для генерации и review, достаточен
для ориентации агента.

## Risks / Trade-offs

- **[Дрейф индекса]** — если Архиватор пропустит обновление, индекс устареет.
  → Mitigation: на данном этапе — ответственность Архиватора; в будущем возможна
  команда `opsx:reindex` для полного пересчёта.

- **[Токены INDEX.md]** — при 50+ тематиках INDEX.md приблизится к лимиту 200 строк.
  → Mitigation: при достижении — вынести domains в отдельный файл или группировать.

- **[Субъективность domain placement]** — AI может предлагать нерелевантные домены.
  → Mitigation: Архиватор всегда утверждает; placement не автоматический.

## Затрагиваемые границы модулей

| Граница | Воздействие |
|---------|-------------|
| `.cursor/skills/` | Новый скилл `capability-index` |
| `openspec/specs/` | Читается для генерации index (read-only) |
| Routing AGENTS.md | Может получить ссылку на скилл (опционально) |

Архитектурное решение (ADR) не требуется — изменение не затрагивает runtime приложения.
