## Context

Артефакты планирования OpenSpec (proposal → spec → design → tasks) сериализуют
решения, но не контекст обнаружения. AI-агент Эксперта к концу планирования
знает, какие файлы читал, какие паттерны увидел, как связаны части системы —
но это знание живёт только в контекстном окне и теряется при закрытии сессии.
See proposal.md — Why.

Формат opsx-команд зафиксирован: frontmatter (name, id, category, description),
пояснительный текст, Guardrails, Steps, формат вывода. Образец — `opsx-index.md`.

`operations.apply.guidance` в `openspec/config.yaml` — массив строк; скилл
`/opsx-apply` уже читает `operationGuidance` из `openspec instructions` и
следует применимым пунктам. Новый guidance будет подхвачен автоматически.

## Goals / Non-Goals

**Goals:**
- Команда `/opsx-terra-firma`, создающая `terra.md` в каталоге change.
- Формат `terra.md` с четырьмя секциями по критериям spec.
- Интеграция с apply через `operations.apply.guidance`.

**Non-Goals:**
- Новый скилл (terra — только команда).
- Правки сгенерированных `.cursor/skills/openspec-*` и opsx-команд.
- Автоматическое создание terra при archive / apply / validate.
- Валидация содержимого terra.md средствами CLI.
- Шаблон terra.md в OpenSpec schema (файл вне цепочки артефактов).

## Decisions

### 1. Только команда, без скилла

**Выбор**: алгоритм живёт в `/opsx-terra-firma` (как `/opsx-index`), не в скилле.

**Альтернативы**:
- Скилл + команда → потребитель (apply-агент) может случайно подхватить
  write-инструкции и начать создавать/менять terra.
- Секция в существующем скилле → нет подходящего скилла; capability-index —
  read-only навигатор, openspec-apply — сгенерированный.

**Обоснование**: apply-агент — потребитель terra.md (читает), не производитель.
Команда явно вызывается Экспертом; потребителю алгоритм создания не нужен.

### 2. Четыре секции по критериям spec

**Выбор**: `terra.md` содержит четыре секции Markdown:
1. **Карта файлов** — таблица: путь, роль в change, действие.
2. **Наблюдения** — факты о коде, обнаруженные при планировании.
3. **Образцы** — файл-образец + что именно в нём паттерн.
4. **Навигация** — порядок чтения от общего к частному.

**Альтернативы**:
- YAML-формат (как topics/*.yaml) → избыточная строгость; содержимое
  свободно-текстовое, YAML добавит шум.
- Единый неструктурированный текст → потребитель не знает, где искать
  конкретный тип информации.
- Формат, привязанный к задачам (по одной карте на задачу) → дублирование
  файлов между задачами; карта территории ортогональна списку работ.

**Обоснование**: четыре секции отражают четыре типа cache miss (где? что рядом?
как принято? куда смотреть дальше?). Формат — Markdown, потребитель читает как
текст. Секции фиксированы по названию, содержимое внутри — свободное.

### 3. Источник данных — контекстное окно AI-агента Эксперта

**Выбор**: команда не делает поиск по репозиторию и не запрашивает внешние
данные. AI-агент формирует terra.md из того, что уже знает: прочитанные файлы,
обнаруженные паттерны, принятые решения — всё, что накопилось за сессию
планирования.

**Альтернативы**:
- Автоматический сбор из git diff / истории → terra превращается в инструмент
  анализа, а не в сериализацию кеша; теряется экспертное знание о ролях.
- Обязательное чтение всех файлов из tasks.md → если агент их уже читал,
  это повторная работа; если не читал, он не может описать их роль.

**Обоснование**: ценность terra — именно в экспертном знании агента, а не
в механическом сборе путей. Агент знает не только ЧТО файл, но и ЗАЧЕМ он
важен для этого change.

### 4. Предусловие — tasks.md

**Выбор**: команда проверяет наличие `tasks.md` в каталоге change. Если
tasks.md нет — предупреждение и отказ. Наличие проверяется файловой системой,
не через `openspec status` (terra вне цепочки артефактов).

**Альтернативы**:
- Проверка через `openspec status --change` → CLI не знает о terra;
  `isPlanningComplete` может не учитывать design/spec, если они skipped.
- Без предусловия → terra можно создать до tasks, но тогда она не покрывает
  задачи и нарушает критерий достаточности.

**Обоснование**: tasks.md — последний артефакт планирования. Если он есть,
planning завершено и AI-агент накопил максимум контекста. Terra до tasks
бессмысленна.

### 5. Резолв change — по контексту чата или аргументу

**Выбор**: команда принимает необязательное имя change
(`/opsx-terra-firma add-auth`). Если опущено — вывести из контекста чата
(только что завершённое планирование). Если неоднозначно — спросить.
Резолв через `openspec list` (для active changes) или каталог
`openspec/changes/`.

**Альтернативы**:
- Только аргумент → лишний ввод, если change только что планировали.
- Только контекст → не работает в новом чате.

### 6. Guidance для apply — одна строка

**Выбор**: добавить в `operations.apply.guidance` строку: «Перед выполнением
задач прочитай terra.md, если он существует в каталоге change.»

Скилл `/opsx-apply` уже читает `operationGuidance` и следует пунктам. Новый
пункт будет подхвачен без правок apply-скилла.

**Альтернативы**:
- Вшить чтение terra в `/opsx-apply` → файл перезаписывается
  `openspec update`.
- Не указывать → apply-агент может не знать о terra.md.

## Алгоритм `/opsx-terra-firma` (для текста команды)

1. Резолвить change (аргумент / контекст чата / спросить).
2. Проверить `tasks.md` в каталоге change. Нет → предупреждение, отказ.
3. Прочитать артефакты change (proposal, spec, design, tasks) для полноты.
4. Сформировать `terra.md` из контекстного окна:
   - **Карта файлов**: все файлы, которые агент знает как относящиеся к change.
     Таблица: путь | роль в change | действие.
   - **Наблюдения**: факты о коде, повлиявшие на решения design.
   - **Образцы**: для каждого паттерна — файл-образец и что в нём паттерн.
   - **Навигация**: порядок чтения от общего к частному.
5. Записать в `<changeRoot>/terra.md`.
6. Сообщить итог. Коммит не делать — Эксперт видит diff в UI.

## Формат `terra.md`

```markdown
## Карта файлов

| Файл | Роль в change | Действие |
|------|---------------|----------|
| `path/to/file` | описание роли | создать / изменить / образец / не трогать |

## Наблюдения

- Факт о коде, обнаруженный при планировании и повлиявший на design.
- Ещё факт.

## Образцы

- `path/to/example` — что именно в нём является паттерном для этого change.

## Навигация

1. `path/first` → что даёт чтение этого файла
2. `path/second` → что даёт чтение этого файла
```

## Risks / Trade-offs

- **[Качество зависит от контекста агента]** — если сессия планирования была
  короткой (fast-forward), terra может быть неполной.
  → Mitigation: terra опциональна; apply работает и без неё.

- **[Terra устаревает при изменении tasks/design]** — если после создания terra
  артефакты пересмотрены, карта может не соответствовать задачам.
  → Mitigation: Эксперт контролирует содержимое; перезапуск команды
  обновит файл.

- **[Нет валидации полноты]** — CLI не проверяет, покрыты ли все задачи.
  → Mitigation: критерии необходимости и достаточности в spec — гайд для
  агента, не машинная проверка. Качество terra — ответственность Эксперта.

## Migration Plan

Появление команды и guidance не требует миграции runtime. Откат — revert
файлов change. Существующие changes не затрагиваются: terra.md опциональна.

## Затрагиваемые границы модулей

| Граница | Воздействие |
|---------|-------------|
| `.cursor/commands/` | Новый `opsx-terra-firma.md` |
| `openspec/config.yaml` | Строка в `operations.apply.guidance` |
| `openspec/specs/terra/` | Новый spec (через delta этого change) |
| `.cursor/skills/openspec-*`, opsx-*.md | Не трогать |
| Runtime PHP | Нет |

Архитектурное решение (ADR) не требуется — runtime приложения не затрагивается.

Brownfield-поведение PHP/legacy не меняется; раздел по `brownfield-map` не нужен.
