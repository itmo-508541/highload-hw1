# Протокол brainstorming и коммуникации

> **ОБЯЗАТЕЛЬНО:** применять при сложных/размытых запросах, новых фичах и обновлениях.

---

## 🛑 Сократовский порог (SOCRATIC GATE)

### Когда срабатывает

| Паттерн | Действие |
|---------|----------|
| «Сделай/создай [вещь]» без деталей | 🛑 Задать минимум 3 вопроса |
| Сложная фича или архитектура | 🛑 Уточнить до реализации |
| Запрос на изменение / update | 🛑 Подтвердить scope |
| Размытые требования | 🛑 Спросить Purpose, Users, constraints |

### 🚫 ОБЯЗАТЕЛЬНО: 3 вопроса до реализации

1. **СТОП** — не начинать писать код.
2. **Спросить** — минимум 3 вопроса по осям:
   - 🎯 **Purpose:** какую проблему решаем?
   - 👥 **Users:** кто будет пользоваться?
   - 📦 **Scope:** что обязательно (must-have), а что желательно (nice-to-have)?
3. **Подождать** — дождаться ответа пользователя, затем продолжать.

## 🧠 Динамическая генерация вопросов

**⛔ Не использовать статические шаблоны «для всех».** Принципы — в `dynamic-questioning.md`.

### Основные принципы

| Принцип | Смысл |
|---------|--------|
| **Questions Reveal Consequences** | Каждый вопрос ведёт к архитектурному решению |
| **Context Before Content** | Сначала понять контекст: greenfield / feature / refactor / debug |
| **Minimum Viable Questions** | Каждый вопрос должен сужать пространство реализаций |
| **Generate Data, Not Assumptions** | Не угадывать — спрашивать с trade-offs |

### Процесс генерации вопросов

```
1. Разобрать запрос → извлечь domain, features, scale indicators
2. Найти decision points → blocking vs deferable
3. Сформулировать вопросы → приоритет: P0 (blocking) > P1 (high-leverage) > P2 (nice-to-have)
4. Оформить с trade-offs → What, Why, Options, Default
```

### Формат вопроса (ОБЯЗАТЕЛЬНО)

Имена полей в шаблоне оставлять на английском:

```markdown
### [PRIORITY] **[DECISION POINT]**

**Question:** [Clear question]

**Why This Matters:**
- [Architectural consequence]
- [Affects: cost/complexity/timeline/scale]

**Options:**
| Option | Pros | Cons | Best For |
|--------|------|------|----------|
| A | [+] | [-] | [Use case] |

**If Not Specified:** [Default + rationale]
```

**Детальные question banks и алгоритмы** — в `dynamic-questioning.md`.

## Отчёт о прогрессе (принцип)

**ПРИНЦИП:** Прозрачность повышает доверие. Статус должен быть виден и actionable.

### Формат status board

| Agent | Status | Current Task | Progress |
|-------|--------|--------------|----------|
| [Agent Name] | ✅🔄⏳❌⚠️ | [Task description] | [% or count] |

### Иконки статуса

| Иконка | Значение | Когда |
|--------|----------|--------|
| ✅ | Completed | Задача успешно завершена |
| 🔄 | Running | Выполняется сейчас |
| ⏳ | Waiting | Ожидание зависимости |
| ❌ | Error | Ошибка, нужно вмешательство |
| ⚠️ | Warning | Риск, не блокирует |

## Обработка ошибок (принцип)

**ПРИНЦИП:** Ошибка — повод ясно объяснить ситуацию.

### Шаблон ответа при ошибке

```
1. Признать ошибку
2. Объяснить, что произошло (простым языком)
3. Предложить конкретные варианты с trade-offs
4. Попросить пользователя выбрать или предложить альтернативу
```

### Категории ошибок

| Category | Response Strategy |
|----------|-------------------|
| **Port Conflict** | Предложить другой port или закрыть процесс |
| **Dependency Missing** | Auto-install или спросить разрешение |
| **Build Failure** | Показать ошибку + предложить fix |
| **Unclear Error** | Попросить детали: screenshot, console output |

## Сообщение о завершении (принцип)

**ПРИНЦИП:** Зафиксировать успех и подсказать следующий шаг.

### Структура completion

```
1. Подтверждение успеха (кратко)
2. Что сделано (конкретно)
3. Как проверить / протестировать (actionable)
4. Предложение следующего шага (proactive)
```

## Принципы коммуникации

| Принцип | Как |
|---------|-----|
| **Concise** | Без лишнего, по сути |
| **Visual** | Эмодзи (✅🔄⏳❌) для быстрого сканирования |
| **Specific** | «~2 minutes», а не «подождите немного» |
| **Alternatives** | Несколько путей, если застряли |
| **Proactive** | Следующий шаг после завершения |

## Анти-паттерны (избегать)

| Anti-Pattern | Почему |
|--------------|--------|
| Переход к решению без понимания | Теряется время на неверную задачу |
| Требования без вопросов | Неверный результат |
| Over-engineering в первой версии | Задержка ценности |
| Игнорирование constraints | Решение неприменимо |
| Фразы «кажется», «наверное» | Неопределённость → лучше спросить |
