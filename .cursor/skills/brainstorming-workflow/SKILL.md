# Workflow субагентов

Цепочка субагентов для сложных задач: декомпозиция → реализация → ревью → документация.

Соблюдай **Human in the loop (HITL)**: между этапами, где требуется решение человека (утверждение плана, согласование рискованных шагов, разрешение спорных замечаний ревью), **останавливайся** и **дождись** явного ввода пользователя; не имитируй согласование между субагентами вместо пользователя там, где это описано в `.cursor/agents/*.md`.

## Когда применять

- Сложная задача (новая фича, рефакторинг, несколько связанных изменений)
- Задача требует планирования и последующей реализации
- Нужна проверка кода и обновление документации

## Последовательность

```
Задача → planner (brainstorming → подтверждение черновика → файл плана) →
  [HITL: пользователь утвердил план и путь к файлу] →
worker (в т.ч. стопы на рискованных шагах) → reviewer →
  [замечания?] → спорные пункты? → [HITL: решение пользователя] → worker … | documenter
```

### 1. Planner

**Файл**: `.cursor/agents/planner.md`

- Читай агента и запусти его как субагент
- Декомпозиция задачи, оценка рисков, архитектурный дизайн
- **Обязательно** выполняет brainstorming (уточняющие вопросы) до плана; при смене scope — явное согласование с пользователем
- **Подтверждение черновика** направления задачи пользователем **до** записи файла плана (см. агент)
- Создаёт план в `.cursor/plans/YYYY-MM-DD-краткое-название.md` только после подтверждения
- Результат: путь к плану для worker

**HITL:** перед вызовом worker пользователь должен **утвердить** итоговый план (и при неоднозначности — **явно указать** путь к файлу плана).

### 2. Worker

**Файл**: `.cursor/agents/worker.md`

- Читай агента и запусти его с путём к плану, согласованным с пользователем
- Реализует план пошагово, без архитектурных решений
- **Старт, рискованные шаги, отклонения от плана** — по правилам Human in the loop в агенте (подтверждение пути к плану, явное ОК на миграции/секреты/API/данные, отклонения только с разрешения пользователя)
- Отмечает выполнение в плане (`- [x]`)
- Пишет тесты в `tests/` или `features/` при изменении или добавлении кода в `src/`
- Результат: изменённый код, обновлённый план

### 3. Reviewer

**Файл**: `.cursor/agents/reviewer.md`

- Читай агента и передай ему git diff / список изменённых файлов
- Проверяет безопасность, стиль, производительность
- **Не пишет код** — только замечания; разделяет **обязательные** и **спорные** пункты
- **Если замечаний нет** — не задавай пользователю лишних вопросов; переходи к documenter

**Два варианта:**

| Исход | Действие |
|-------|----------|
| Есть замечания (в т.ч. спорные) | Обязательные — передать worker на исправления. По **спорным** — **решение пользователя**, затем при необходимости worker → reviewer снова |
| Замечаний нет | Перейти к documenter **без** дополнительного запроса к пользователю |

### 4. Documenter

**Файл**: `.cursor/agents/documenter.md`

- Вызывать **только** после одобрения reviewer (замечаний нет)
- Читай агента и выполни скилл `@.cursor/skills/update-rules/SKILL.md`
- Обновляет: `CHANGELOG.md`, `skills.mdc`, `README.md`
- Сообщает о завершении задачи

## Чеклист выполнения

- [ ] planner: brainstorming (при необходимости) и подтверждён пользователем черновик направления; план записан в `.cursor/plans/`
- [ ] пользователь утвердил план и (при неоднозначности) путь к файлу плана перед worker
- [ ] worker реализовал все шаги с учётом HITL (рискованные шаги, отклонения от плана), отметил в плане
- [ ] reviewer: замечаний нет **или** устранены обязательные замечания и приняты пользователем решения по спорным
- [ ] documenter обновил документацию по update-rules
- [ ] Задача завершена

## Цикл reviewer ↔ worker

При замечаниях reviewer передаёт список worker: сначала **обязательные** пункты; по **спорным** — после решения пользователя worker вносит согласованные правки или фиксирует обоснованный отказ. Reviewer проверяет снова. Цикл до состояния «замечаний нет» (без лишних вопросов пользователю при чистом проходе).
