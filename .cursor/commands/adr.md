Создай новую запись архитектурного решения (Architecture Decision Record).

## Инструкции

1. Определи следующий порядковый номер ADR, посмотрев существующие файлы в `adr/`.
2. Создай файл `adr/NNNN-<slug>.md`, где `NNNN` — номер с ведущими нулями, `<slug>` — краткое название решения через дефис (латиницей, строчными буквами).
3. Используй `adr/0000-adr-template.md` как образец структуры и стиля.
4. Заполни все разделы:
   - **Статус**: `Предложено` (по умолчанию). Другие допустимые значения: `Принято`, `Отменено`, `Заменено ADR-NNNN`. При обновлении статуса существующего ADR также допустимо: `Дополнено ADR-NNNN`.
   - **Дата**: дата создания в формате `YYYY-MM-DD`.
   - **Контекст**: опиши силы и обстоятельства, вынуждающие принять решение. Язык нейтральный, только факты. Упоминай технологические, организационные и проектные факторы.
   - **Решение**: сформулируй решение в активном залоге («Мы будем…», «Используем…»). Полные предложения, не буллеты.
   - **Обоснование**: объясни, почему именно это решение является лучшим ответом на описанный контекст.
   - **Рассмотренные альтернативы**: перечисли отвергнутые варианты и кратко укажи причину отказа от каждого.
   - **Последствия**: все последствия — позитивные, негативные, нейтральные. Не скрывай компромиссы.
   - **Связанные артефакты**: ссылки на связанные ADR, документы, issues, PR или внешние ресурсы.

## Связь с OpenSpec change

Если ADR создаётся в рамках активного change в `openspec/changes/<name>/`:

- Типичная точка: после `design.md`, до или во время заполнения `tasks.md`.
- В `tasks.md` должна быть явная задача на создание/принятие ADR (если решение архитектурное).
- В «Связанные артефакты» укажи путь к change (например `openspec/changes/<name>/`).
- Не создавай ADR «на каждый» change: только для значимых долгоживущих решений.

## Иммутабельность принятых ADR

ADR — это лог решений. Тело принятого ADR **нельзя редактировать**. Все разделы кроме «Статус» фиксируются в момент принятия и остаются неизменными навсегда, даже если содержат устаревшую информацию. Устаревание фиксируется через новый ADR, а не через правку старого.

Единственное допустимое изменение в существующем ADR — раздел **«Статус»**:

- Значение статуса может быть изменено (например, `Принято` → `Заменено ADR-0006`).
- Под значением статуса может быть добавлен ненумерованный список с пояснениями, что именно было дополнено, уточнено или отменено. Каждый пункт должен содержать ссылку на ADR, в котором зафиксировано новое решение. Ссылки на другие файлы проекта в этом списке не допускаются.

Пример:

```markdown
## Статус

Принято

- Команда `/pause` отменена — [ADR-0006](0006-subagent-constraints-and-pause-cancellation.md)
- Открытый вопрос о субагентах решён — [ADR-0006](0006-subagent-constraints-and-pause-cancellation.md)
```

При создании нового ADR **проверь**, затрагивает ли новое решение какие-либо ранее принятые ADR. Если да — обнови раздел «Статус» затронутых ADR по правилам выше.

## Требования к стилю

- Документ должен быть на 1–2 страницы. Краткость важнее полноты.
- Пиши как для будущего разработчика, который ничего не знает о текущем контексте.
- Используй русский язык.
- Не добавляй секции, которых нет в шаблоне.

## Опциональные секции MADR

Если решение сложное и требует детального сравнения альтернатив, можно добавить:

- **Факторы, определяющие выбор** — после раздела «Контекст».
- **За и против** — подразделы внутри каждой альтернативы в разделе «Рассмотренные альтернативы».

Добавляй эти секции только когда они действительно помогают, а не для галочки.
