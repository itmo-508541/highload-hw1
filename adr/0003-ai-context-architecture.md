# ADR-0003: Архитектура AI-контекста проекта

## Статус

Принято

## Дата

2026-08-20

## Контекст

AI-агенты работают с проектом через agent harness (Cursor и аналоги). Harness автоматически подгружает файлы `AGENTS.md` по иерархии каталогов и `.cursor/rules/*.mdc`, а скиллы вызываются явно по триггеру.

Проект накопил контекстные файлы стихийно: скиллы содержат и декларативный контекст (факты, конвенции), и процедурные инструкции (шаги рабочего цикла). Дублирование между скиллами и `AGENTS.md` приводит к рассогласованию и шуму. Скилл `run-php-in-docker` решает проблему Docker-запуска, но вынуждает harness загружать его при каждой PHP-операции через always-applied rule — overhead, который устраняется однострочным constraint в `AGENTS.md`.

Нужна устойчивая схема размещения AI-контекста, которая минимизирует дублирование, доставляет контекст автоматически (без явного вызова скилла) и масштабируется при переносе шаблона в рабочие проекты.

## Решение

Используем пятислойную модель AI-контекста.

| Слой | Файл | Содержит | Доставка |
|------|------|----------|----------|
| 1. Корень | `AGENTS.md` | Constraints, карта каталогов, стек | Автоматически |
| 2. Каталог | `<dir>/AGENTS.md` | Конвенции и факты области | Автоматически при работе в каталоге |
| 3. Скилл | `.cursor/skills/<name>/SKILL.md` | Пошаговый workflow, чеклист | Явно, по триггеру |
| 4. Rule | `.cursor/rules/*.mdc` | Жёсткие always-on ограничения | Автоматически |
| 5. OpenSpec | `openspec/config.yaml` context | Паспорт проекта (стек, бандлы) | OpenSpec CLI при генерации артефактов |

Критерий разделения AGENTS.md и Skill: если агент **нарушит** без прочтения — это AGENTS.md (constraint/fact). Если **не сможет выполнить действие** без руководства — это Skill.

Дублирование стека (~1 строка) между root `AGENTS.md` и `openspec/config.yaml` — осознанный компромисс: разные потребители (agent harness vs OpenSpec CLI), формальная синхронизация не требуется.

В текстах `AGENTS.md` используем термин «agent harness» вместо имени конкретного инструмента.

## Обоснование

Каскадное чтение `AGENTS.md` по иерархии каталогов — встроенная механика agent harness. Constraints и конвенции в `AGENTS.md` видны агенту автоматически при работе с каталогом. Скиллы подгружаются явно — в них уместны только пошаговые инструкции, не нужные при каждом обращении.

Один root-файл для constraints + вложенные файлы для деталей каталогов — баланс между полнотой и шумом. Ориентир для root: 35–50 строк.

## Рассмотренные альтернативы

- **Всё в скиллах.** Контекст не виден агенту без явного вызова; дублирование с `AGENTS.md` неизбежно. Скилл `run-php-in-docker` — пример: always-applied rule вынужденно перенаправляет в скилл при каждой PHP-операции.
- **Всё в root `AGENTS.md`.** >100 строк, шумно, нарушает каскадный принцип, не масштабируется.
- **Только rules (.mdc).** Подгружаются автоматически, но не предназначены для структурированного каталожного контекста и не поддерживают каскад.

## Последствия

- Скиллы `phpunit-tests` и `behat-tests` облегчаются: декларативный контекст переезжает в `tests/AGENTS.md` и `features/AGENTS.md` соответственно.
- Скилл `run-php-in-docker` и связанный always-applied rule удаляются. Docker-constraint — в root `AGENTS.md`.
- Каталоги `migrations/` и `bin/` получают свои `AGENTS.md`.
- Создаётся always-on rule `vendor-class-lookup.mdc` для constraint'а, который агент должен видеть всегда.
- При создании проекта из шаблона `AGENTS.md`-файлы переносятся вместе с кодом без дополнительной настройки.
