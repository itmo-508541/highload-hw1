# features/

Behat: сценарии на Gherkin и контексты к ним.

## Домены

Домен — предметная область сценария: о чём сценарий, а не на чём он написан.
Техническая платформа доменом быть не может: она не даёт о сценарии никакой
информации. Ось крупная: доменов единицы, а не десятки. Домена «нет» не бывает;
не виден из задачи — спросить у пользователя.

| Домен | О чём | Feature-файлы | Контекст |
|---|---|---|---|
| `admin_access` | граница аутентификации: куда попадает не вошедший посетитель и кого форма входа пускает в административный интерфейс | `features/admin_access_*.feature` | `AdminAccessContext` |

Пополняется строкой в этой таблице. Каноническая запись домена — `snake_case`;
имя контекста получается из неё переводом в `PascalCase` плюс суффикс `Context`.
Новый домен заводится **вместе с первым своим сценарием**, не заранее.

## Имена файлов

`features/<домен>_<поведение>.feature`, целиком `snake_case`. Префикс обязан
быть доменом из таблицы выше. `<поведение>` — краткое описание проверяемого
поведения, и то же поведение читается в заголовке `Feature:`.

Суффикс **не называет формат и не называет технологию**: они о поведении
не сообщают ничего — тот же критерий, по которому техническая платформа
не годится в домены.

## Теги

| Тег | Где | Когда |
|---|---|---|
| `@domain:<домен>` | на `Feature` | всегда |
| `@javascript` | на `Feature` или на `Scenario` | актор действует через браузер с JS |

`@javascript` ставится на `Feature`, если браузер нужен всем сценариям файла,
и на отдельные `Scenario`, если хотя бы одному он не нужен. Смешанный файл
допустим: фильтр по тегам режет по сценариям, а не по файлам.

Suite в `behat.yml.dist` один, отбор срезов — тегом:

```bash
vendor/bin/behat --tags='@javascript'    # браузерные
vendor/bin/behat --tags='~@javascript'   # остальные
```

## Сессии

| Тег сценария | Сессия | Что поднимается | Окружение |
|---|---|---|---|
| `@javascript` | `panther` | свой веб-сервер и Chrome | `e2e` |
| без `@javascript` | — | **пока не настроена** | — |

Сессия `symfony` (ядро в том же процессе, без браузера) появится вместе
с первым сценарием без `@javascript`: ей нужен пакет
`behat/mink-browserkit-driver`, которого в проекте ещё нет.

## Конфигурация

- `behat.yml.dist` (локально: копия → `behat.yml`, не коммитить).
- Bootstrap — `tests/bootstrap.php`, расширение `FriendsOfBehat\SymfonyExtension`,
  ядро в `test`.
- Контексты — `features/bootstrap/`, namespace `App\Behat\`. Новый контекст
  регистрируется в `behat.yml.dist`; без ключа `contexts` Behat подставит
  дефолтный `FeatureContext` и упадёт.
- Фикстуры — `./fixtures/` относительно `*Context.php`.
- Шаги — атрибуты `#[When]` / `#[Then]`. Паттерн шага уникален глобально:
  точный дубль роняет Behat на загрузке. Подходящий шаг переиспользуется.

```bash
make behat                            # все сценарии
make behat features/foo.feature       # один файл
```

## Где живёт шаг

1. Шаг, использованный **более чем одним доменом**, — в общем контексте.
2. Остальные — в контексте своего домена.

Общего контекста сейчас нет: домен один.

## Куда не класть

- OpenSpec specs → `openspec/` (не сливать с `features/`)
- Unit/integration PHPUnit → `tests/`
- Проверки сборки, phing-задач и изолированной логики → `tests/`: у них нет
  актора вне команды разработки
