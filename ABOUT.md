## Проблема и цель

Дашборды Grafana для сервиса с множеством ручек дорого вести руками: каждая
новая ручка — ещё набор панелей latency, traffic и errors. Работа HW1
показывает обратный подход — метрики собираются идиоматичным средством стека,
а дашборд генерируется скриптом.

Состав работы:

1. **Подготовительная часть** — микросервис ровно с тремя REST-ручками над
   записями и служебной ручкой готовности, завёрнутый в Docker Compose.
2. **Часть 1** — экспорт золотых сигналов (latency, throughput, errors)
   с каждой ручки в формате Prometheus по `GET /metrics`.
3. **Часть 2** — генератор дашборда Grafana по метрикам ручек.
4. **Часть 3** — скрипт «обстрела»: небольшая нагрузка на ручки сервиса.

Успех — дашборд, сгенерированный скриптом, показывает перцентили, RPS и ошибки
по каждой ручке под нагрузкой, в том числе при агрегации по нескольким
экземплярам сервиса.

## Основные возможности системы

- `POST /items` — создать запись из тела `{"value": <скаляр>}`, ответ
  `201 {"id": N}`.
- `GET /items/{id}` — прочитать запись, ответ `200 {"value": X}` того же
  JSON-типа, что был записан; для несуществующего id — `404`.
- `PUT /items/{id}` — заменить значение существующей записи, ответ
  `200 {"id": N}`; для несуществующего id — `404`, запись не создаётся.
- `GET /health` — `200`, когда хранилище записей доступно, иначе `503`.

Значение — строка, целое, дробное или `true`/`false`; тело другого вида —
`400`. Ответы, включая ошибки, — JSON. Ручки доступны без аутентификации.
Нормативное поведение — `openspec/specs/items/` и `openspec/specs/health/`.

## Архитектура системы

- Ручки — Symfony-контроллеры по одному на ручку (`src/Controller/Item/`,
  `src/Controller/HealthController.php`); ответы и ошибки сериализует FOSRest.
- Записи хранятся в Redis, а не в памяти процесса, как предлагает задание:
  под PHP-FPM память не переживает запрос, а несколько экземпляров сервиса
  должны делить записи и нумерацию id. Обоснование —
  [ADR 0004](docs/adr/0004-items-stored-in-redis.md).
- Ключи Redis: `items:seq` (счётчик id) и `item:{id}` (значение JSON-строкой).
- Метрики, `/metrics`, генератор дашборда и нагрузочный скрипт появятся
  в следующих частях работы.

## Сценарии использования

```bash
curl -s -X POST http://localhost/items -H 'Content-Type: application/json' -d '{"value":"foo"}'
curl -s http://localhost/items/1
curl -s -X PUT http://localhost/items/1 -H 'Content-Type: application/json' -d '{"value":42}'
curl -s http://localhost/health
```

Для приёмки критичны: уникальность id, сохранение JSON-типа значения,
`404` без upsert на `PUT`, `400` на невалидное тело без изменения хранилища,
`503` на `/health` при недоступном хранилище. Приёмочные сценарии —
`features/item_storage_*.feature`, `features/service_health_*.feature`.

## Ограничения и допущения

- Жёсткий дедлайн работы — 30 октября 2026 г., 23:59 UTC+3.
- Хранилище — Redis вместо in-memory (ADR 0004). При недоступном Redis ручки
  `/items` отвечают `500`, `/health` — `503`.
- Нет удаления, листинга и TTL записей. Одновременная замена одной записи
  не защищена: последний `PUT` выигрывает.
- Клиент обязан слать `Content-Type: application/json`: без него тело
  не разбирается и запрос получает `400`.
- Целые за пределами `PHP_INT_MAX` декодируются во `float`; дробное с нулевой
  дробной частью (`1.0`) может вернуться как `1`.
- Секреты production не хранятся в репозитории; реальные значения — в CI
  и/или серверном окружении.
