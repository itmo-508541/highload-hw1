# Дамп env (`.env.local.php`) только в demo-режиме, не в dev

На production приложение читает env только из дампа `.env.local.php`, который
собирает CI. Demo-режим (prod-образ без override) должен показывать то же
поведение, поэтому в нём дамп собирает обязательный сервис `init` при каждом
старте, а php читает его через шим. Хотелось сделать так же и в dev — один путь
загрузки env во всех режимах.

Мешает `dotenv_overload: true` (`composer.json` → `extra.runtime`; тот же режим
явно включают `tests/bootstrap.php` и `tools/phing-bootstrap.php`). С ним
`Dotenv::bootEnv()` применяет существующий `.env.local.php` безусловно, вместе
с записанным в нём `APP_ENV`. В dev проект смонтирован целиком, и один дамп
в корне видят все процессы контейнера: phpunit (`APP_ENV=test`), Phing
с `-Dapp.env=test`, приложение под Panther (`e2e`). Все они молча ушли бы
в окружение дампа — тесты писали бы в dev-базу, а `bin/console --env=…`
падал бы с `LogicException` из Symfony Runtime.

Решено: дамп создаётся **только в demo**. Dev грузит цепочку `.env`-файлов как
раньше, `dotenv_overload` не меняется. Сервис `init` в dev выключен: профиль
`disabled` и команда-заглушка `false`. Инициализацию dev выполняет `make init`
(`phing` в контейнере `php`). Унаследованная из базового файла команда собрала бы
дамп, а заглушка ничего не делает и при случайном запуске завершается ошибкой.
Что сломается, если дамп появится в dev, фиксирует
`tests/Integration/TestEnvironmentTest.php`.

Demo повторяет production-путь без CI:

- `init` при **каждом** старте заново собирает дамп в именованный том `dotenv`.
  Устаревшего дампа не бывает, и правка `.env*` применяется перезапуском.
- Дамп собирается из цепочки `.env` → `.env.local` → `.env.prod` →
  `.env.prod.local` (оба `.local` — если есть) в порядке Symfony `loadEnv`, как
  `composer symfony:dump-env` в CI, где `.env.prod.local` формируется из
  GitLab-переменных. `.env.local` даёт локальные переопределения demo, но
  `.env.prod` перекрывает его. Без `.env` сборка падает.
- Собирает дамп скрипт `tools/env-dump.php` с явным списком файлов и парсером
  Symfony Dotenv. Проект смонтирован в `init` только на чтение: скрипт сам
  выбирает файлы, лишнее в дамп не попадает.
- В `php` нет `.env`-файлов. Шим `secrets/env-demo.php`, смонтированный как
  `/srv/.env.local.php`, подключает дамп из тома тем же приёмом, что
  `secrets/env.php` на production, и отличается от него только путём.
- `init` выполняет `phing` после дампа, а `php` стартует только после успешного
  `init`. Bootstrap Phing читает свежий дамп через шим и видит ровно то, что
  увидит приложение. Битый `.env*` роняет `init`, а не даёт работающее
  приложение без env.

## Considered Options

- **Отключить `dotenv_overload`** — отвергнуто в рамках этого решения: тогда
  Symfony штатно игнорирует дамп с чужим `APP_ENV`, но одновременно переменные
  контейнера начинают перекрывать `.env` во всех режимах. Это меняет решение,
  ради которого overload включали, и требует отдельного разбора.
- **Dev-шим, подключающий дамп только при `APP_ENV=dev`** — отвергнуто:
  самописная логика выбора окружения вместо штатной, которую придётся
  поддерживать рядом с поведением Dotenv.
- **Дамп в demo создавать только при отсутствии и хранить на хосте** —
  отвергнуто: правка `.env*` молча не применялась бы, а bind-каталог, который
  Docker создаёт сам, принадлежит root, и `init` под `www-data` не пишет в него.
- **Собирать дамп штатными средствами** — отвергнуто:
  - `bootEnv` прочитал бы прежний дамп через шим, и новый собрался бы из старого;
  - `loadEnv` при отсутствии `.env` молча берёт `.env.dist`, а `.env` обязателен;
  - `composer symfony:dump-env` недоступен: composer есть только в dev-образе;
  - `dotenv:dump` пишет рядом с `.env`, а `/srv` в demo только для чтения.
- **Phing-цель сборки дампа** — отвергнуто: bootstrap Phing вызывает `bootEnv`
  до любой цели и прочитал бы прежний дамп.
- **Монтировать в `init` отдельные `.env`-файлы** — отвергнуто: bind
  несуществующего `.env.prod.local` Docker превратил бы в root-каталог на хосте.
- **`php` зависит от `init` с `required: false`** — отвергнуто: так php
  стартует и после упавшего `init`. В dev вместо этого override снимает
  зависимость (`depends_on: !override`).

## Consequences

- Загрузка env в dev и в demo/production различается сознательно; demo
  и production совпадают: шим `/srv/.env.local.php` → дамп, `.env`-файлов в php нет.
- В demo правка `.env*` применяется только перезапуском, и перезапуск — это
  `docker compose down` и `docker compose up -d`. `up -d` поверх запущенного demo
  не останавливает уже работающий php: если `init` упадёт, php продолжит
  отдавать прежний дамп.
- `docker compose up php --no-deps` обходит порядок и поднимает php с дампом
  прошлого успешного старта.
- В dev `init` не участвует ни в каком сценарии; базовый файл задаёт зависимость
  `php` от `init`, поэтому dev-override обязан её снимать.
- Ручной `.env.local.php` в корне dev-проекта по-прежнему перекрывает
  `APP_ENV` всех процессов — `TestEnvironmentTest` краснеет первым.
- Пересмотр решения начинается с вопроса об `dotenv_overload`, а не с dev-режима.
