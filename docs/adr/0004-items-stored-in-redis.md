# Записи `/items` хранятся в Redis, а не в памяти процесса

Задание HW1 (`HW1.md`, «Подготовительная часть») предлагает in-memory
хранилище: данные в структурах рантайма. Для долгоживущего процесса
(Go, Java, Node.js) это работает — запрос за запросом обслуживает один и тот же
процесс, и его память переживает запрос. Сервис написан на PHP под PHP-FPM,
а PHP-FPM устроен по модели share-nothing: каждый запрос исполняется
с чистого листа, всё созданное в нём уничтожается вместе с запросом, а пул
воркеров ещё и раздаёт запросы разным процессам. Запись, сделанная
`POST /items`, к следующему `GET /items/{id}` в памяти уже не существует.

Кроме того, части 1–3 работы предполагают несколько экземпляров сервиса
(метки пода и датацентра, агрегация перцентилей по экземплярам, обстрел
нагрузочным скриптом). Даже долгоживущий процесс держал бы у каждого
экземпляра свои записи и свою нумерацию id.

Решено: **записи хранятся в Redis**, который уже есть в стеке (на нём
лежат сессии). Ключи — `items:seq` (счётчик id, `INCR`) и `item:{id}`
(значение JSON-строкой `{"value": X}`, чтобы сохранялся JSON-тип). Замена —
`SET … XX`: проверка существования и запись одной командой, `PUT` не создаёт
запись. Готовность сервиса (`GET /health`) определяется доступностью Redis:
`PING`.

Это отход от буквы задания, но не от его цели: задание просит каноническую
имплементацию простого CRUD-хранилища, а не именно память процесса.

## Considered Options

- **In-memory (массив в PHP)** — отвергнуто: под PHP-FPM данные не переживают
  запрос, ручка `GET` никогда не находила бы записи.
- **APCu** — разделяемая память в пределах одного пула PHP-FPM ближе всего
  к «in-memory» из задания, но расширения в образе нет, кеш не виден CLI
  и тестам Behat, а у каждого контейнера `php` он свой: несколько экземпляров
  выдали бы пересекающиеся id. Очистка кеша при нехватке памяти молча теряет
  записи.
- **Файл на диске** — отвергнуто: нужна своя блокировка для атомарной выдачи
  id, файл живёт в контейнере и не делится между экземплярами без общего тома,
  а под нагрузкой части 3 блокировка файла становится узким местом.
- **MySQL (Doctrine)** — тоже в стеке и тоже общий, но для «ключ — значение»
  избыточен: нужна сущность, схема, ORM на каждый запрос, а скалярное значение
  произвольного JSON-типа в колонку ложится только строкой с ручным разбором.

## Consequences

- Экземпляры сервиса с общим Redis делят записи и нумерацию: id уникальны
  между экземплярами за счёт атомарного `INCR`. Неудачная запись после `INCR`
  оставляет дыру в нумерации — уникальность обещана, непрерывность нет.
- Сервис зависит от Redis. При его недоступности ручки `/items` отвечают 500,
  а `/health` — 503: по нему зависимые сервисы могут не направлять трафик
  к экземпляру. Healthcheck compose на `/health` пока не заведён.
  Для части 3 работы это естественный источник 5xx.
- Записи переживают перезапуск контейнера `php` и лежат в томе `redis-data`
  вместе с сессиями. Тестовое окружение пишет в отдельную БД Redis и очищает
  её перед каждым сценарием Behat.
- Латентность ручек включает сетевой вызов к Redis — в метриках части 1 это
  будет видно, и это честнее памяти процесса для сервиса, рассчитанного
  на несколько экземпляров.
