# Symfony backend

Проект backend на Symfony 7.4 / PHP 8.4 с локальной разработкой в Docker и деплоем через GitLab CI/CD.

## Технологический стек

- PHP `8.4`
- Symfony `7.4.*`
- MySQL `8.0`
- Docker / Docker Compose
- Composer
- Phing (инициализация, подготовка storage, миграции, deploy-команды)
- QA-инструменты: PHP CS Fixer, PHPStan, Rector, PHPUnit, Behat

## Быстрый старт

```bash
make up
make init
```

Установка и обновление зависимостей (Composer в контейнере `php`):

```bash
make deps
```

Проверки перед commit:

```bash
make qa
```

Подробности смотри в [документации](docs/symfony/init.md).

## Принципы работы backend-разработчика

- Пишите и проверяйте код в Docker-контуре проекта, чтобы окружение совпадало у команды и в CI.
- **Команды, затрагивающие PHP и инструменты вокруг него** (Composer, Symfony Console, PHPUnit, Behat, Phing, PHP CS Fixer, PHPStan, Rector и т.п.) **выполняйте только** в сервисе `php` (контейнеры должны быть запущены, см. раздел «Локальный цикл разработки» и `make up`). **Не** запускайте их на хосте из корня проекта — иначе версии PHP, расширений и пути разойдутся с CI и продом. Сначала смотрите цели **`make`** и [`README.md`](../../README.md); если подходящей цели нет — `docker compose exec php …` из корня репозитория. Примеры: `make deps` или `docker compose exec php composer install`.
- **Владелец файлов на хосте:** образ сервиса `php` по умолчанию запускается от пользователя **`www-data`** (`Dockerfile`). Если **не** задать **`user`** в локальном **`docker-compose.override.yml`**, то и процесс контейнера, и **`docker compose exec php …`**, и файлы, созданные в смонтированном проекте (`./:/srv`), на хосте будут с владельцем **`www-data`** — неудобно для правки из-под своего пользователя. Скопируйте **`docker-compose.override.yml.dist`** в **`docker-compose.override.yml`** (второй файл в `.gitignore`, не коммитится) и подставьте свой **`uid`/`gid`** (`id -u`, `id -g`) в поле **`user`**, чтобы владелец совпадал с вашим аккаунтом на машине. Если владелец файлов каким-то образом оказался другим, выполните **`make owner`** — цель выравнивает владельца дерева под текущего пользователя (внутри вызывается `sudo`; см. комментарий к цели в `Makefile`).
- Файлы репозитория внутри контейнера `php` смонтированы в `/srv/` (пути от корня проекта на хосте совпадают с ожидаемыми в командах ниже).
- Структура таблиц и индексы создаются автоматически, создавать новые миграции для этого не нужно; миграции Doctrine в проекте используются для добавления или изменения **данных**.
- Соблюдайте единый стиль кода (`.editorconfig`, `.php-cs-fixer.dist.php`) и не обходите проверки качества.
- Перед merge обязательно прогоняйте QA-набор (`php-cs-fixer`, `phpstan`, `rector`, `phpunit`, `behat`).
- Любые изменения схемы БД сопровождайте корректным циклом миграций и проверкой на локальном окружении.
- Не храните production-секреты в репозитории и в коммитах. Для production используются CI-переменные и серверные env-файлы.
