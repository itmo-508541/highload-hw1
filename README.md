# Symfony backend

Проект backend на Symfony 7.4 / PHP 8.4 с локальной разработкой в Docker и деплоем через GitLab CI/CD.

## Технологический стек

- PHP `8.4`
- Symfony `7.4.*`
- MySQL `8.0`
- Docker / Docker Compose
- Composer
- Phing (инициализация, подготовка storage, миграции, deploy-команды)
- QA-инструменты: PHP CS Fixer, PHPStan, Rector, PHPUnit, Behat

## Быстрый старт

```bash
cp docker-compose.override.yml.dist docker-compose.override.yml
make up
make init
```

Установка и обновление зависимостей (Composer в контейнере `php`):

```bash
make deps
```

Проверки перед commit:

```bash
make qa
```

Подробности смотри в [документации](docs/symfony/init.md).

## Начало работы

После шага из раздела «Быстрый старт» у вас уже есть локальный **`docker-compose.override.yml`** (его нет в репозитории: файл в **`.gitignore`**, создаётся копированием **`docker-compose.override.yml.dist`**).

В поле **`user`** задайте **`"<uid>:<gid>"`**, подставив вывод команд **`id -u`** и **`id -g`** на вашей машине. Тогда процесс сервиса **`php`** и файлы, которые приложение или **`docker compose exec php …`** создают в смонтированном каталоге **`./:/srv`**, на хосте будут принадлежать вашему пользователю.

Если **`user`** не задавать, образ по умолчанию работает от **`www-data`** (`Dockerfile`) — новые файлы на хосте окажутся с владельцем **`www-data`**. Если владелец дерева проекта всё же «съехал», из корня репозитория выполните **`make owner`** (внутри используется `sudo`; см. комментарий к цели в `Makefile`).

## Принципы работы backend-разработчика

- Пишите и проверяйте код в Docker-контуре проекта, чтобы окружение совпадало у команды и в CI.
- **Команды, затрагивающие PHP и инструменты вокруг него** (Composer, Symfony Console, PHPUnit, Behat, Phing, PHP CS Fixer, PHPStan, Rector и т.п.) **выполняйте только** в сервисе `php`. **Не** запускайте их на хосте — иначе версии PHP, расширений и пути разойдутся с CI и продом. Сначала смотрите цели в **`Makefile`**; если подходящей цели нет — `docker compose exec php …` из корня репозитория. Примеры: `make deps` или `docker compose exec php composer install`.
- Файлы репозитория внутри контейнера `php` смонтированы в `/srv/` (пути от корня проекта на хосте совпадают с ожидаемыми в командах ниже).
- Структура таблиц и индексы создаются автоматически, создавать новые миграции для этого не нужно; миграции Doctrine в проекте используются для добавления или изменения **данных**.
- Соблюдайте единый стиль кода (`.editorconfig`, `.php-cs-fixer.dist.php`) и не обходите проверки качества.
- Перед merge обязательно прогоняйте QA-набор (`php-cs-fixer`, `phpstan`, `rector`, `phpunit`, `behat`).
- Не храните production-секреты в репозитории и в коммитах. Для production используются CI-переменные и серверные env-файлы.

## Эксперимент с файловой системой

В **`docker-compose.yml`** включён режим **`read_only: true`** для **`php`** и **`nginx`**. В **`docker-compose.deploy.yml`** **`read_only: true`** задан для **`nginx`**, **`php`** и **`spare`** (корень файловой системы контейнера только для чтения по отношению к слою образа).

Это эксперимент по ужесточению контейнеров; при сбоях его можно временно выключить, вернувшись к понятному сообщению об ошибке.

### Последствия для **php**

- **Корень контейнерного дерева «запечатан»**: нельзя создавать файлы и каталоги внутри путей, которые лежат только в слоях образа (или стали недоступны из‑за read-only родителя). Любая запись приложения или расширения PHP должна попадать в **отдельно смонтированный том** (**volume** / bind mount) или во **временное хранилище** (**tmpfs**).
- **`tmpfs` в Compose** задаёт виртуальный диск в RAM: у сервиса **`php`** смонтирован **`/tmp`** — туда уже уходит **`pid`** php-fpm и прочая временная работа процесса, если конфиг это предусматривает. Всё, что приложение напрямую пишет в **`/tmp`** (или в другие чисто «локальные» каталоги вне тома и без **`tmpfs`**), упадёт с ошибкой записи (**Read-only file system**, **Permission denied**) — тогда нужен ещё **`tmpfs`** на этот путь или смена пути в конфиге (например **`upload_tmp_dir`** в **`php.ini`**).
- **`volumes`** в Compose монтируют отдельные файловые системы; по умолчанию они **читаемо-записываемые**, если не указано **`ro`**. Поэтому локально том **`.:/srv`** по-прежнему позволяет писать в **`var/cache`**, **`var/log`** и т.д.; read-only ограничивает запись именно по путям **вне тома**.
- На **production** приложение чаще **без** bind mount всего **`/srv`**: тогда возможны ошибки записи там, где раньше случайно писался кэш/логи в каталог образа без отдельного тома — типичное решение: **выделить том** под **`var/`**, **`storage`** или нужные подкаталоги (один или несколько **`volumes`** в Compose) либо согласовать с образом только чтение кода (**`:ro`** на приложение и отдельный **rw**‑том на **`var`**).

### Если что‑то сломалось — во что смотреть

1. Журнал контейнера и ответ приложения (**500**, сообщения PHP о невозможности создать файл).
2. Путь записи из текста ошибки: если это не **`/srv/...`** (том) и не **`/tmp`** (**tmpfs**), добавить **`tmpfs`** на нужный абсолютный путь **или** вынести данные во **volume** **или** направить параметр приложения на уже доступный writable каталог.
3. Если нужна запись только в subset дерева (**загрузки**, **sessions** в файловых сессиях): отдельный смонтированный каталог **умнее**, чем весь доступный образ.

### Справка по томам (**volume** против **tmpfs**)

| Механизм | Что это | Где использовать |
|---------|---------|-------------------|
| **tmpfs** | Очистится при пересоздании контейнера; быстро | **`/tmp`**, pid, временные буферы, то, что не нужно сохранять между пересозданиями контейнера |
| **volume** / bind mount | Данные на диске хоста (или том Docker); сохраняются | **`var/cache`**, логи, загрузки, долгоживущее состояние |

Краткий принцип: **read-only** заставляет явно решить для каждой записи: **этот файл должен быть в томе или в tmpfs.**
